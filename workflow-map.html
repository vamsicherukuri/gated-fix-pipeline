GitHub Copilot App Enterprise Challenge — Workflow Architecture, Week 1 Draft

Gated Fix Pipeline

An eleven-step bug-fix-to-merge workflow with two hard human checkpoints, a bounded agent retry loop, and a cheap early check that keeps expensive stages from running on bad input. Three mechanisms carry the governance and efficiency story: Intake Triage blocks planning until the issue has real acceptance criteria and a declared scope; the Scope Gate blocks the Developer agent from starting until a PM approves in plain language; and the Develop → Test → Review loop is capped at three attempts before it escalates rather than burning tokens indefinitely. Cross-package impact is caught by a zero-token deterministic search, not a dedicated agent — an agent was designed for this and then cut once it stopped earning its cost (see the efficiency notes below). Agent roles

Each stage's input is the prior stage's structured output, never the raw issue re-read from scratch — that's what stops two agents from quietly redoing the same work and burning tokens twice. What each agent reads, writes, and escalates to is what feeds the permissions/audit readout at the Merge gate.

Intake Triage

Checks the issue is ready and scoped before anything expensive runs.

ReadsIssue text only
WritesNothing — no repo access
EscalatesPM, after 2 clarification rounds

Architect

Turns an approved issue into a scoped technical plan — no code.

ReadsRepo, bounded to scope + one hop
WritesNothing — plan only, no code
EscalatesN/A — feeds the Scope gate

Implements exactly what Architect's plan specified.

WritesOwn branch only, scope-enforced

ReadsDiff, Developer's tests

Judges whether the diff should ship — flags only.

ReadsDiff + any zero-token sweep hits

Release-helper

Triages CI logs, executes the approved merge, and reverts on a confirmed regression.

ReadsCI status + logs, pre- and post-merge
WritesMerge, and revert + new issue on genuine failure

Efficiency mechanisms

Bounded retry, not an open loop

Steps 5–7 can hand back to the Developer agent at most 3 times. A 4th failure doesn't spend a 4th round of tokens — it escalates to the PM and the pipeline pauses. This is the single biggest lever on runaway cost, since an unbounded fix↔test loop is where multi-agent workflows typically bleed tokens.

Governance is a permissions/audit readout

Rather than a plain approval log, step 9's governance surface shows what each agent's scoped tool and repo access actually was during the run — alongside the per-stage token counts above — so a reviewer sees both what an agent could touch and what it cost in one place.

Search is cheap, context is not

Repo indexing/search (grep, code search) costs no LLM tokens regardless of repo size — the token cost only comes from pulling file contents into context to reason over. So the declared-scope field on every issue doesn't stop agents from searching; it stops them from loading irrelevant packages into context after they search. A dedicated Impact Auditor agent was designed to catch cross-package impact, then cut in favor of a zero-token grep sweep that only escalates to Reviewer when it finds something — the design catching its own over-engineering, not just avoiding it upfront.

Observations: free or forgotten

When an agent notices something unrelated to the current issue, token cost — not usefulness — decides what happens: if logging it is a free byproduct of work already done, it's auto-filed as a low-priority issue; if logging it would take any further investigation or reasoning, the agent drops it and moves on. No agent may expand scope just to make a finding loggable.
